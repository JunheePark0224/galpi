# 프로젝트 설계·운영 설명서 (갈피에서 정리한 방식)

Last Updated: 2026-10-28

**지키는 것은 날짜가 아니라 순서다.** 날짜는 모두 잠정이고, 일찍 끝나면 다음 단계를 바로 이어 한다.

## 2. 단계별

### 0. 주제 고르기
- 후보마다 **고객 / 문제 / 분석으로 보여 줄 수 있는 것**을 한 줄씩. 데이터가 실제로 모이는지(이용자 행동이 생기는지)를 먼저 본다.
- 경쟁 서비스를 직접 써 보고 관찰한 것만 적는다(원칙 "과장하지 않는다").
- 이전에 멈춘 프로젝트가 있으면 그 회고의 체크리스트부터 읽는다(`Kkeutjang/docs/retrospective.md`).

### 1. 기획안 (`proposal.md`)
- 고객(가상이어도 구체적으로 — 갈피는 "YES24 추천 기획자"), 문제, 해결 아이디어, **무엇을 측정하고 어떻게 분석할지**.
- 판을 거듭하면 옛 판은 `docs/archive/`로.

### 2. PRD
- 기획안을 번호로 쪼갠다: **기능 `F-xx`, 화면 `S-xx`, 이벤트 `E-xx`, 데이터 `D-xx`**. 화면마다 어떤 기능·이벤트가 붙는지 표로.
- 정하지 못한 것은 "미정" 목록에 모으고 **하나씩 사용자에게 물어** 닫는다(갈피는 v0.1 미정 5개 → v0.2 확정).
- 이후 규칙: **PRD에 없는 기능은 만들지 않는다. 기능을 바꾸면 PRD 먼저.**

### 3. PHASES
- 트랙을 나눈다: 🛠 개발(P0~), 🎨 디자인, 📚 데이터(D1~), 📊 분석.
- 단계마다 **완료 기준**을 적는다. 화면 단계의 완료 기준에는 "그 화면의 이벤트가 제대로 쌓이는가"를 넣는다.

### 4. DESIGN + 문서 관계
- **원칙 몇 줄**(갈피: 책이 주인공, 심플하게 조금 귀엽게, 다른 브랜드와 닮지 않게, 다크 모드 없음).
- **토큰 T**: 콘셉트에서 바탕·글자·강조색을 고르고, **글자 대비를 계산**(WCAG AA 4.5 : 1 이상). 범주 색(갈피는 장르)은 흰 글자 대비 + 서로 구분(색차 ΔE)도 확인.
- **컴포넌트 C, 에셋 A**: 핵심 부품의 규격을 글로(갈피 책갈피: 아치 창 + 제비꼬리 + 끈).
- **`docs/README.md`**: 문서끼리 무엇을 정하는지, 바꿀 때 어떤 순서로 고치는지, ID 추적표.

### 5. 레퍼런스·시안
- 참고 이미지는 `docs/references/`(참고 전용, 저작물은 쓰지 않는다).
- 디자인 결정은 **HTML 시안 2~3개를 나란히** 만들어 고르게 한다(`docs/mockups/날짜-이름.html` + 스크린샷). 말로 묻지 않는다.

### 6. Stitch 화면 설계
1. Stitch 공식 형식 확인: `npx -p @google/design.md designmd spec`.
2. `docs/stitch/DESIGN.md`를 원본 DESIGN에서 **파생**해 쓴다: 위 YAML에 `version`·`name`·`description`·`colors`(역할 이름)·`typography`·`rounded`·`spacing`·`components`(토큰을 `{colors.x}`로 참조), 아래 본문에 Overview·Colors·Typography·Layout·Elevation & Depth·Shapes·Components·Do's and Don'ts. 같은 도구로 **검사 오류 0 · 경고 0**까지.
3. `STITCH-PROMPTS.md`: 영어 프롬프트 + 화면 글자는 한국어, 기준 크기(모바일 390 × 844). **P-00은 핵심 부품 시트**(갈피 책갈피 6종) → 화면 프롬프트 하나씩 → "하지 말 것"을 명시 → 수정 프롬프트 몇 개.
4. 사용자가 stitch.withgoogle.com에서 생성 → `.env`에 `STITCH_API_KEY`(사용자가 직접 입력) → `src/stitch_client.py` + `src/fetch_stitch.py`(읽기 전용, 키 출력 안 함)로 화면 PNG·HTML을 `docs/stitch/exports/`에 수집.
5. `exports/README.md`에 화면별 체크, **가져갈 것**, **따르지 않을 부분**(기획에 없는 문구·기능 — 갈피는 11건). 시안 HTML은 쓰지 않고 참고만 해서 다시 구현한다.

### 7. 프로젝트 CLAUDE.md
- 세션을 이어갈 때 읽을 순서, 문서와 ID 표, **원칙**(어기지 않는 것 — 번호로), 폴더 구조, 기술, 보안·약관, 디자인 규칙, 사용자와 일하는 방식.
- 운영하며 생긴 규칙은 바로 여기에 원칙으로 더한다(갈피 원칙 6·7).

### 8. 구현 계획
- `superpowers:writing-plans` 방식: **로드맵**(단계 진행 절차, 폴더 구조, **단계 사이에 바꾸지 않을 인터페이스**: 타입·함수·이벤트 스키마·DB 표) + **첫 단계 상세 계획**(태스크마다 테스트 먼저).
- 계획 속 코드를 임시 폴더에서 **실제로 돌려** 검증한다(갈피 P1: 테스트 49개, 커버리지 100%).
- 기준 버전(Node·프레임워크)을 그날 확인해 적는다.

### 9. P0 셋업
- git: 비밀(`.env`)과 원문 데이터(API 원본)는 처음부터 제외.
- 앱 뼈대(갈피: Next.js), 테스트(Vitest + Playwright 휴대폰·노트북), 디자인 토큰 CSS.
- **기록을 먼저 심는다**: 이벤트 스키마 + `track()` 하나 + `/api/track` + DB 표 → 첫 방문이 저장되는지 확인.

### 10. 이벤트·Amplitude
- **원본은 `docs/taxonomy.md`** (이벤트 이름·속성·허용값·언제 보내나) → `taxonomy.csv` → 코드의 명세 하나(`schema.ts` `EVENT_SPEC`) → 테스트 → `track()` 호출. 바꿀 때 **이 순서로 같은 커밋**. 문서·csv·코드가 같은지 자동 테스트로 검사.
- 저장: **Supabase `events`가 원본**, 같은 이벤트를 브라우저에서 Amplitude로 사본. 익명 번호를 Amplitude `device_id`로.
- 개인 정보가 될 수 있는 값(직접 쓴 글 등)은 **Supabase에만**, Amplitude 사본에서는 뺀다. 처리방침(`/privacy`)에 모으는 항목을 모두 공개.
- Amplitude: 키는 **Production에만**(사용자가 Vercel에 입력), Session Replay 20%·입력 가림, 프로젝트 시간대 Asia/Seoul, 커넥터로 이벤트 카탈로그 등록, 핵심 지표 대시보드.
- 공통 속성(회차 round, 세션, 처음/다시 온 사람, 기기)은 처음에 정한다 — 나중에 바꾸면 분석이 끊긴다.

### 11. 단계별 구현 + 데이터 트랙
- 구현: 계획 → 태스크마다 구현 → **스펙 리뷰 → 코드 리뷰** → 완료 기준 확인 → 병합(`superpowers:subagent-driven-development`). 동시 작업은 `.worktrees/<이름>`.
- 데이터(사람이 기준, AI는 그대로 붙이기): **기준표(정의서)를 사람이 쓰고**, AI 둘이 따로 태그해 **일치율(κ)**을 재고, 갈리는 것만 사람이 검수, 일치한 것 중 **표본**도 사람이 본다. 검수에서 나온 결정은 기준표 버전을 올려 적는다(갈피 `label-dictionary.md` v3 → v3.11).
- 추천·계산 로직은 화면과 떨어진 순수 함수 + 테스트 100%, 파이썬 시뮬레이션과 같은 분포.

### 12. 배포 전 점검·첫 배포
- 처리방침, 보안(같은 출처, 분당 한도, 크기 상한, 보안 헤더), 비용 상한(AI 호출).
- **공개 저장소면 기록 전체 검사**(키·실명·원문) — 갈피는 첫 공개 전에 기록에서 지울 것을 지웠다.
- 배포 후 점검(200/404, 보안 헤더, 한 바퀴 완주, DB 저장). 공개 전에 **5명 반응**을 받는다.
- 공개 점검표·용량 추정·개인정보 확인: `docs/launch/`.

### 13. 공개·운영
- **매일 아침 숫자**: SQL 몇 개만(일별·주간 사용자, 실험 현황, 업데이트 소식 열람, 로그인). 내 기기는 늘 뺀다.
- **피드백 창구**(갈피 우체통)와 받은 피드백 기록(`feedback/`).
- **업데이트 소식**(갈피 소식통): 이용자에게 보이는 변경을 배포할 때마다 그 주에 한 줄. 진행 중인 실험은 쓰지 않는다.
- 콘텐츠를 늘리는 일(갈피: 책 추가)은 **절차를 문서로 고정**해 반복한다(`HANDOFF.md` 3-1).
- 배포는 사용자가 "배포해줘"라고 할 때만, 배포 시각을 기록.

### 14. 분석·실험
- **실험 전 기준선 기간**을 정해 퍼널·멈춘 곳을 먼저 본다 → 가설.
- A/B: 지표 하나(갈피: 책갈피를 본 사람 중 책 정보까지 간 비율), 필요 표본 수, **판정일을 하루로 미리 정하고 중간에 멈추지 않는다**(피킹 금지), 실험 중 **바꿔도 되는 화면 / 안 되는 화면**을 적고, 바꾼 배포 시각을 기록해 전후로 나눠 본다.
- 결론은 **차이의 크기 + 95% 신뢰구간**(사람 단위 부트스트랩·Newcombe). "유의하다"로 단정하지 않는다. 표본이 모자라면 모자랐다고 쓴다.

### 15. 발표
- `report/outline.md`(흐름) → `report/storyboard.md`(장마다 제목 = 결론 한 문장, 화면, 말할 것, 준비할 것).
- 장표는 스킬 **`canva-deck`**(GitHub `JunheePark0224/canva-deck-skill`): HTML 장표 → 스크린샷 점검 → Canva로 가져오기. 청중 가독성 규칙 포함.

### 16. 인수인계
- `HANDOFF.md`: 지금 상태, 열린 일, 반복 작업 절차(명령어 그대로), 하지 않는 것, 저장소 밖 파일. `context.md`: 날짜·결정·이유.
- 세션 메모에만 있는 규칙은 CLAUDE.md로 옮긴다.

## 3. 갈피에서 효과를 본 원칙

1. **문서 → 코드 순서, ID로 연결.** PRD의 F·S·E가 PHASES·DESIGN·taxonomy·테스트까지 같은 번호로 이어진다.
2. **기록은 처음부터, 화면과 함께.** 분석 프로젝트에서 이벤트는 기능이다.
3. **기준은 사람이, AI는 그 기준대로.** 그리고 일치율과 표본으로 확인한다.
4. **결정은 시안으로, 기록은 바로.** 고른 이유는 `context.md`에 그날.
5. **과장하지 않는다.** 관찰한 것과 확인된 것을 구분하고, 숫자는 범위와 함께.
6. **절차는 문서로 고정.** 반복 작업(콘텐츠 추가, 배포, 매일 확인)은 명령어까지 적는다.

## 4. 겪은 함정

- 시안 도구(Stitch)는 기획에 없는 문구·기능을 지어낸다 → 받자마자 기획과 대조.
- 규칙이 "이름만" 있고 뜻이 없으면 AI가 갈린다(갈피: "웹소설", "만화") → 넣는 것 / 빼는 것 / 예시를 같이 적는다.
- 설정 기본값과 실행 옵션이 다르면 잊는다(갈피: 책 50권 기본값) → 자주 쓰는 값은 기본값으로.
- ISBN 같은 키가 달라도 같은 것일 수 있다(같은 책 다른 판) → 다른 단서(저자·쪽수·제목)로 한 번 더.
- 숫자 지표의 정의(갈피: "다시 온 사람"이 세션 기준이라 첫날에도 생김)를 확인하지 않으면 해석이 틀린다 → 정의를 SQL과 함께 적는다.
- 배포 권한·키 입력·콘솔 설정은 사용자 몫 → 사용자가 할 일은 "무엇을·어디에·어떤 값"까지 적어 준다.
